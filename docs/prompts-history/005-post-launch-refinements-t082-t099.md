# Process Log 005: Post-Launch Refinements (T082–T099)

**Covers**: everything from the user's first live (non-demo, real-credential) run through a ten-prompt live grading pass — eighteen tasks (T082–T099) spanning quick fixes, one significant architecture revision made deliberately with the user, and two rounds of "the same symptom came back, go deeper" diagnosis — for feature `001-streaming-discovery-assistant`.

**Purpose of this document**: see Process Log 001 — a condensed, high-level record of reasoning, decisions, and course-corrections, not a transcript.

## 1. The first live run: three quick, independent bugs

Polish had shipped with 100% fixture-backed test coverage but zero live exercise of the real TMDB/OpenRouter adapters. The first live run found three unrelated issues fast: `.env`'s `MODEL_NAME` was an invalid OpenRouter slug (`deepseek/deepseek-chat-v4-0731`; the correct one, confirmed against three independent sources, is `deepseek/deepseek-v4-flash-0731`); `pydantic-ai`'s startup banner was being mistaken for an error; and the terminal gave no indication of which pipeline phase was running. All three were fixed quickly (T082–T084) — the third by adding a purely-informational `on_step` callback to the Orchestrator, deliberately kept free of any decision-making so it didn't touch the determinism boundary.

## 2. The first real bug: TMDB was never actually being queried correctly

A request naming a provider or genre returned nothing. The cause was a documented-but-never-finished placeholder in `RealTmdbClient.discover()`: genre and provider **names** were being sent straight through as query parameters, but TMDB's discover endpoint requires numeric ids. No test had ever caught this because every test exercises the fixture-backed fake client, which ignores query parameters entirely — this was the first time the real adapter's query construction had ever run at all (T086). Fixed with real id resolution for both (provider matching against a live, cached fetch of TMDB's own provider list; genre matching against the existing static genre tables), with a "fail closed rather than silently drop" rule for providers specifically, since they're a hard constraint.

The same live run also showed vibe-only requests (no genre, no liked titles) returning TMDB's generic popularity list with no relationship to the request — spec-compliant (the Recommendation Agent correctly flagged the weak matches) but a poor result in practice, since the Discovery Agent had always deliberately excluded subjective fields entirely. This was a real, considered architecture decision, not a bug fix: after discussing three options with the user, `vibe_keywords` was added, wiring tone/setting/theme descriptors into TMDB's own keyword search as a genuinely TMDB-native filter — a deliberate, documented revision of the Discovery Agent's contract, not a workaround (T087).

A separately-found bug: the confirmation-correction prompt read terminal input while the status spinner's background thread was still actively repainting the same line, making typed corrections hard to see (T088).

## 3. A deeper investigation: "not Marvel or DC" produced a Marvel title anyway

A request excluding Marvel/DC still recommended Spider-Man as Best Match, and a "hopeful, superhero" request's Wildcard Pick was an unrelated romance. Rather than patch the exclusion in isolation, the user pushed back explicitly on a first-pass fix ("is it really as simple as fixing X? I feel like that's fixing the symptom but not the issue") and pointed at a specific tell: the model's own rationale could recognize a pick was wrong and still present it. That led to tracing the actual mechanism rather than the symptom, surfacing three separate, compounding gaps: `additional_notes` (where the Marvel/DC exclusion landed, since it isn't a TMDB genre) was captured but read by nothing downstream, not even the rationale prompt; `vibe_keywords` OR'd a fuzzy tone word together with theme descriptors, letting a noisy tone-keyword match alone satisfy the discovery filter; and `RecommendationAgent`'s selection had no relevance floor at all — it always filled three slots by score, regardless of how irrelevant the best available candidate was.

Four fixes followed, each targeted at one of these (T089–T092): tone dropped from the discovery-side keyword filter entirely (tone stays a ranking signal, never a hard filter); `additional_notes` wired into the rationale prompt so the model is at least aware of what it's ignoring; a real `excluded_keywords` field with server-side TMDB enforcement plus defense-in-depth text matching; and a relevance floor on `theme_descriptors`. The relevance floor's own implementation self-corrected mid-task: the original plan also gated on `setting_descriptors`, which broke an existing test encoding spec.md's own User Story 2 acceptance criteria (a vague, tone/setting-only request must still surface a weak, honestly-flagged pick, not get filtered to nothing) — narrowed to theme only once that test caught the conflict, and the correction was written into the task record rather than smoothed over.

Separately, guided intake was changed to skip a question already answered by free text (T085), after discussion of three implementation options with real cost/precision tradeoffs — landing on skipping the three single-field questions outright while previewing (not skipping) the two compound ones, since skipping those could silently drop whichever of their several fields free text didn't cover.

## 4. The same symptom came back — twice — and each time the actual cause was one layer deeper

A second live run on the same "Superhero movie, not Marvel or DC" request still failed the same two ways. This time the cause was confirmed to be two things: `excluded_keywords` had never been wired into either confirmation display, so a captured exclusion was invisible and uncorrectable (T093); and the system prompt's instruction for a non-genre term ("superhero") only said "descriptive mood or vibe," which didn't cue the model to route a *subject* word there — it was landing nowhere at all, which explains both symptoms at once, since the relevance floor had nothing to gate on when `theme_descriptors` came back empty (T094).

With the user's explicit go-ahead, a live re-verification (real TMDB/OpenRouter, not fixtures) confirmed the extraction and display fixes worked — the confirmation table correctly showed the exclusion and theme — but Spider-Man *still* won Best Match. Pulling the film's actual TMDB data directly showed why: its real overview and keyword tags never mention "Marvel" at all, so neither the text-match check nor TMDB's own keyword filter could ever have caught it — but its `production_companies` field does say "Marvel Entertainment." A third, independent defense layer was added against that field specifically, since it's the one TMDB reliably populates with actual studio/publisher identity (T095). A related, separately-reported bug — the confirmation-correction prompt silently doing nothing on unrecognized input, and a genuine crash risk on a syntactically-valid-but-invalid correction — was fixed the same session (T096).

A third live scenario (a pre-1970 animated family request) surfaced two more instances of the same underlying pattern: "classic" — a reputation/era word, not subject matter — was being sent to TMDB's keyword search as a hard filter, collapsing a real 45-result query to zero (T097); and "cartoon animation" wasn't being normalized to the official genre "Animation," loosening a filter that was supposed to be tight (T098). Both verified by fetching the real, unfiltered TMDB result counts directly and confirming the exact query change that caused the collapse, rather than assuming. This run also included a pasted external analysis proposing a six-level cascading relaxation policy and a "guaranteed non-empty results" design; both were declined outright as direct conflicts with this project's own deliberate, spec-documented principles (exactly one bounded retry; a hard constraint is never relaxed even to avoid an empty result) — the analysis's own claimed root cause also didn't match what the codebase actually did once checked against the real confirmation output.

## 5. A ten-prompt grading pass, and a rationale-fidelity bug

At the user's request, ten varied live prompts (specific to vague, spanning exclusions, similarity, guided-intake-only, and deliberately open-ended requests) were run end-to-end and graded on constraint fidelity, relevance, and diversity. Two of ten surfaced a new, more serious bug: a role's displayed title and its written rationale described two different titles entirely — both times on the weakest-fitting candidate in the pool, consistent with the model quietly substituting a better-fitting title it knew from training data instead of honestly critiquing the one it was actually given.

The fix converts this from a hard-to-detect free-text failure into something code can verify: the model's structured output now includes a required `for_title` field it must echo back verbatim, checked deterministically against the actual candidate before the rationale is trusted, with one corrective retry and a safe generic fallback if it still doesn't match — never surfacing a wrong-title rationale (T099). Verified live against the exact case that first showed the bug.

## 6. What this phase changed about how this project works

Every fix in this phase after the first few was found and confirmed against the *real* TMDB/OpenRouter APIs, not just the fixture suite — several diagnoses were only possible by fetching a specific real title's actual data and checking exactly which query parameter change collapsed a real result count. The user's standing instruction through this whole phase was consistent: don't stop at the first plausible fix, and treat a discrepancy between what the system's own reasoning says and what it actually does as a signal that a deeper, separate cause is still there. Two proposed fixes were declined specifically because they conflicted with this project's own earlier, deliberate architecture decisions (the retry bound; never relaxing a hard constraint to avoid emptiness) — those principles held even under real pressure to just make a bad result go away.

**Result**: 205 tests passing, lint/format clean, all 18 tasks in this phase checked off with the same discipline the rest of the project has kept — including two entries (T092, T097) that document a mid-task correction rather than only the fix that survived.
